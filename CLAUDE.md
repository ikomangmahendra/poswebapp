# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a Laravel 13 app (repo name `poswebapp` — intended as the base for a point-of-sale web application), built out module by module. Category (`app/Models/Category.php`) is the first domain module and establishes the conventions below; Product (`app/Models/Product.php`) is the second and adds a `belongsTo`/`hasMany` relationship to Category on top of the same conventions — follow their shape for new full-CRUD modules rather than inventing a new pattern. A Dashboard (`app/Http/Controllers/DashboardController.php`) was added as a non-CRUD, read-only aggregate view over Category/Product data — see the "Aggregate/dashboard endpoints" note below for how that differs from the CRUD module shape. Transaction (`app/Models/Transaction.php`/`TransactionItem.php`) is a third, deliberately create-only module (a sale: line items snapshot each product's price and decrement its stock) — see the "Create-only modules with real business logic" note below. User (`app/Models/User.php`) is a fourth full-CRUD module, retrofitted onto the `User` model/migration/factory Laravel ships by default rather than scaffolded fresh — see the "User management" note below for its one real deviation (the hashed `password` field) and why it has no delete guard yet. Authentication (workshop 07) is wired up on top of that: session-based login/logout via Laravel's default `web` guard, every web page and every `api.php` endpoint (except the framework's default `/api/user`) now requires a session — see the "Authentication" note below for the stateful-API wiring this required.

Each workshop has a detailed write-up in `docs/workshop-0N-*.md` (e.g. `docs/workshop-07-authentication.md`) — check there for the step-by-step reasoning behind a module if this file's summary isn't enough.

## Stack

- PHP ^8.3, Laravel ^13.17, Laravel Sanctum ^4.0 (API token auth, installed but unused so far)
- SQLite by default (`database/database.sqlite`), config supports mysql/mariadb/pgsql/sqlsrv via `.env`
- Frontend build: Vite + Tailwind CSS v4 (`resources/css/app.css` shared by every page; no shared JS *entry* — each page loads only its own module's JS file registered in `vite.config.js`, see "Frontend" below — though entry files may still `import` small non-entry helper modules, e.g. `resources/js/csrf.js`), no JS framework (React/Vue) installed
- Session driver: database; Queue driver: database; Cache: database

## Architecture notes

- Routing is registered in `bootstrap/app.php` via `Application::configure()->withRouting(...)` (Laravel 11+ style, not the old `Http/Kernel.php`): `routes/web.php`, `routes/api.php`, `routes/console.php`, plus a health-check at `/up`.
- Middleware and exception handling are configured inline in `bootstrap/app.php` (`withMiddleware`, `withExceptions`) rather than in separate Kernel/Handler classes.
- API requests get JSON error responses automatically (`shouldRenderJsonWhen` checks `api/*` paths or `expectsJson()`).
- Test environment (`phpunit.xml`) forces SQLite in-memory DB, array cache/session, sync queue, and disables Pulse/Telescope/Nightwatch regardless of `.env`.
- Every web page route and every `api.php` endpoint requires authentication (see "Authentication" below) — any Feature test hitting one needs `$this->actingAs(User::factory()->create())`, typically in the test class's `setUp()`.

## Module conventions (established by Category, extended by Product and Transaction)

Each domain module is a standard Laravel resource stack, wired as follows:

- **API**: `Route::apiResource('categories', CategoryController::class)` in `routes/api.php` (prefixed `/api` automatically); one `Route::apiResource(...)` line per module (e.g. `products`). Controllers are plain resource controllers (`index`/`store`/`show`/`update`/`destroy`) with no service layer — validation lives in `FormRequest` classes, response shaping in `JsonResource` classes. A module that shouldn't support every action (Transaction is create-only — a sale record isn't edited or deleted) chains `->only([...])` onto `apiResource` (`->only(['index', 'store', 'show'])`) so the restriction is an enforced routing fact, not just an unwritten convention — requesting `PUT`/`DELETE` on such a route gets Laravel's normal `405`, not a `404` or a controller method nobody wrote.
- **Validation**: separate `Store{Model}Request` and `Update{Model}Request` in `app/Http/Requests`. `authorize()` currently always returns `true` (no policies yet). Update requests use `sometimes` + `Rule::unique(...)->ignore($this->route('category'))` so a record can keep its own value on update; store requests use a plain `unique:table,column` rule.
- **Responses**: one `{Model}Resource` (`app/Http/Resources`) per model; `index` optionally filters with `->when($request->string('search')->trim()->toString(), fn ($query, $search) => $query->where('name', 'like', "%{$search}%"))`, sorts via `->orderBy($sort, $direction)` where `$sort`/`$direction` come from `?sort=`/`?direction=asc|desc` validated against a column whitelist (`['name', 'updated_at']`) — an unrecognized `sort` resets *both* sort and direction back to the default (`updated_at`, `desc`), it doesn't keep a stray `direction` from the invalid request — then `->paginate(15)->withQueryString()` — 15 per page is the module's standard (server-side, via Laravel's built-in paginator; the JSON response's `meta`/`links` blocks drive the frontend, there is no separate `?per_page=` override), `store` returns the resource wrapped with `->response()->setStatusCode(Response::HTTP_CREATED)`.
- **Tests**: one `tests/Feature/{Model}Test.php` per module using `RefreshDatabase`, hitting the JSON API directly (`getJson`/`postJson`/`putJson`/`deleteJson`) — covers list, create, validation failures, duplicate-name rejection, show, update (including "update with own existing value" and duplicate-name rejection), and delete.
- **Seeders**: `{Model}Seeder` combines a handful of named, meaningful records (via `firstOrCreate`, so re-seeding is idempotent) with a larger batch of `{Model}::factory()->count(N)->create()` (e.g. 45 for Category, for 50 total) so the paginated list has enough rows to exercise multiple pages including a partial last page. `DatabaseSeeder` calls seeders in FK dependency order (`CategorySeeder` before `ProductSeeder`). When a factory's default definition points a foreign key at `RelatedModel::factory()` (as `ProductFactory` does for `category_id`), bulk-seeding with the plain default spawns one brand-new related row *per* created row instead of reusing the ones already seeded — `ProductSeeder` avoids this by overriding `category_id` with `->sequence(fn () => ['category_id' => fake()->randomElement($categoryIds)])` against the real, already-seeded category IDs.
- **Relationships**: Product's `belongsTo(Category::class)` (and Category's matching `hasMany(Product::class)`) is the reference pattern for any FK relationship. The owning side's resource (`ProductResource`) nests the related record as `'category' => ['id' => ..., 'name' => ...]` rather than just the FK id, and the controller's `index`/`show`/`update` eager-load it (`->with('category')` on the query, `->load('category')` on a single model) to avoid an N+1 query per row. Deleting the "many" side of a relationship that still has dependents must not surface a raw DB constraint error: the FK migration column still declares `restrictOnDelete()` as the real guarantee, but the owning controller's `destroy()` checks for a dependent first and returns a friendly `409` naming it (e.g. `CategoryController::destroy()` checks `$category->products()->first()` before deleting) — the same two-layer pattern (DB constraint as backstop + application-level check for UX) already used for unique `name` validation.
- **Frontend**: each module gets its own set of vanilla-JS entry points registered in `vite.config.js`'s `input` array (e.g. `resources/js/categories.js`, `resources/js/categories-form.js`) — not the shared `app.js`. Pages are split by concern rather than combined into one: a list page (`{module}/index.blade.php`) rendering a `#search-form` (just a `#search` input with `minlength="3"` — no submit button, since debounce covers keystroke search and Enter still submits a single-input form), a table with a clickable sortable column header (e.g. `#sort-name`, toggling asc/desc with a `▲`/`▼` indicator span) + "New" link, and a `#pagination` div, calling the JSON API via fetch with `?page=`/`?search=`/`?sort=`/`?direction=` query params — search fires both on debounced keystroke (~300ms) and on submit (Enter), sharing one `applySearch()` guard that rejects non-empty values under 3 characters (an empty value clears the search); the current search term and sort/direction are retained across page navigation and delete-then-refetch, and changing sort resets to page 1 — and driving Prev/Next buttons + a "Page X of Y" label off the response's `meta` block (edit → link to the edit route, delete → confirm + `DELETE` fetch then re-fetch the current page); and a shared create/edit form page (`{module}/form.blade.php`, routes named `{module}.create` and `{module}.edit`) that Blade-renders existing values when a model instance is passed in and reads the record id off a `data-*-id` attribute on the form to decide `POST` vs `PUT`, redirecting back to the list page on success. When the form has a required FK field (e.g. Product's `category_id`), the `{module}.create`/`{module}.edit` web routes fetch the full related-model list server-side (`Category::orderBy('name')->get()`) and pass it to the view, which Blade-renders as a plain `<select>` (disabled placeholder option, `@selected(...)` on edit) — simple and fine at this scale; a searchable/paginated picker would be the natural upgrade once a module has too many related rows for one dropdown. Name the list route `{module}.list`, not `{module}.index` — `Route::apiResource` in `api.php` already auto-registers `{module}.index` for the JSON index endpoint, and since `web.php` loads before `api.php` (`bootstrap/app.php`), a same-named web route silently loses the name and `route('{module}.index')` resolves to the API URL instead. There is no SPA/router — each page is its own server-rendered view backed by its own JS file. All list pages `@include('partials.nav')` (`resources/views/partials/nav.blade.php`) — a plain `<nav>` with one link per top-level page (Dashboard/Categories/Products/Transactions/Users) — so every top-level page is reachable from every other one; a new module adds one line there.
- **Aggregate/dashboard endpoints**: not every controller is a CRUD resource — `DashboardController` is a plain (non-resource, no `Route::apiResource`) controller with one action per concern: `index()` returns a bespoke plain array (not a `JsonResource`, since it doesn't represent one model) of cheap summary stats (`total_products`, `total_categories`, `inventory_value` via `selectRaw('SUM(...) as total')->value('total')`, `low_stock_count`); `lowStock()`, `categoryBreakdown()`, and `recentProducts()` are separate paginated endpoints (`?page=`, 10/page — smaller than a module list's 15, since a dashboard shows several sections on one screen), each routed individually in `api.php` (`/dashboard`, `/dashboard/low-stock`, `/dashboard/categories`, `/dashboard/recent-products`). `lowStock`/`recentProducts` reuse `ProductResource::collection(...)` (same nested-category eager-loading pattern as `ProductController`) so paginating a "top N" list is exactly the same shape as a module's list page. `categoryBreakdown()` has no model-specific Resource class to reuse (it maps `Category::withCount('products')` results to a `{id, name, product_count}` shape) — calling `->through($mapper)` on the paginator transforms `data` but returns Laravel's *flat* pagination array (`current_page`/`total` at the top level), not the nested `{data, links, meta}` shape every list page's JS expects; wrapping the transformed paginator in `JsonResource::collection(...)` restores the standard nested shape without needing a bespoke Resource class. The frontend (`dashboard/index.blade.php` + `dashboard.js`) fetches `index()`'s stats once, then runs three independent paginated sections via a shared `createPaginatedSection({apiUrl, tableBodyId, paginationId, columnCount, emptyMessage, renderRow})` helper — the same Prev/Next-off-`meta` pattern as `categories.js`/`products.js`, generalized so it isn't rewritten three times in one file.
- **Create-only modules with real business logic**: Transaction (a sale) is the reference for a module that only ever gets created and read, never edited or voided. Its `store()` doesn't call `Model::create($request->validated())` directly — it calls `Transaction::createFromItems($items, $user)`, a static model method wrapping `DB::transaction(...)` that: locks each referenced product with `Product::query()->lockForUpdate()` (a plain `DB::transaction()` alone isn't enough to stop two concurrent requests both reading stale stock and overselling — the row lock is what actually prevents that), snapshots `unit_price` from the product's *current* price onto the line item (so a later price change never rewrites history), decrements `stock`, and accumulates the header's `total`. **Business logic used from more than one entry point belongs on the model, not duplicated per-caller**: `TransactionController::store()` and `TransactionSeeder` both call `createFromItems()` — the seeder is not a second copy of the stock-decrement/total-math (it picks a random already-seeded `User` id instead of an `Auth::user()`, since seeding has no request/session). Still no separate service-layer class (`CLAUDE.md`'s "no service layer" stays true — this is a model method, not a new architectural layer). A business-rule failure raised from deep inside that model method (insufficient stock) is a custom exception (`App\Exceptions\InsufficientStockException`) with its own `render($request)` method returning the friendly `422` — the controller doesn't need a `try/catch`, Laravel's exception handler calls `render()` automatically. On the schema side, `transaction_items.transaction_id` uses `cascadeOnDelete()` (a line item has no meaning without its parent transaction) while `transaction_items.product_id` uses `restrictOnDelete()` like every other historical-reference FK in this app, extended once more into `ProductController::destroy()`'s guard (`$product->transactionItems()->first()`) alongside the existing Category one — **the rule of thumb**: cascade when the child row has no independent existence, restrict when the child row is independently meaningful history. Not every module needs every list feature either — Transaction's index has no search box, since there's no natural text field to search a transaction by. `transactions.user_id` (added in a follow-up migration, `2026_08_17_090000_add_user_id_to_transactions_table.php` — the first migration in this app to `Schema::table()` an existing table rather than `Schema::create()` a new one) is a required, `restrictOnDelete()` FK to whoever was authenticated when the sale was rung up: `TransactionController::store()` passes `$request->user()`, `TransactionResource` nests it the same `{id, name}` way as Product's `category`, and the guard this required — `UserController::destroy()` now checks `$user->transactions()->first()` before deleting, the same two-layer FK-restrict-plus-friendly-409 pattern as Category/Product — is `User`'s first delete guard (it had none before, per the "User management" note below).
- **User management (retrofitted onto Laravel's default User)**: unlike Category/Product/Transaction, `User` (model, migration, factory) already existed before this module — `UserController`/`StoreUserRequest`/`UpdateUserRequest`/`UserResource`/`UserSeeder`/routes/tests/views were added around it rather than generated together with `make:model`. The one real deviation from the established pattern is the `password` field: it's validated with `Illuminate\Validation\Rules\Password::defaults()` plus the built-in `confirmed` rule (matching `password_confirmation`), and never hashed explicitly in the controller — `User`'s `casts()` declares `'password' => 'hashed'`, so `create()`/`update()` hash it automatically (idempotently, via `Hash::isHashed()`), the same "the cast owns the storage rule" idea as Product's `'price' => 'decimal:2'`. On update, the `password` rule is `sometimes` (not `nullable`) so omitting the key entirely leaves the hash untouched — the frontend (`resources/js/users-form.js`) is what decides whether to include `password`/`password_confirmation` in the request body at all (only when the user actually typed one), rather than the backend special-casing an empty string. `index()`'s search matches `name` **or** `email` (the first module with a multi-column search), grouped in a nested closure (`->where(fn ($q) => $q->where(...)->orWhere(...))`) so the two conditions stay parenthesized together in the generated SQL. `UserResource` omits `password` explicitly even though the model's `#[Hidden(['password', 'remember_token'])]` attribute already would. **Delete guard on `users`**: now that `transactions.user_id` (see the "Create-only modules with real business logic" note above) is the first foreign key pointing at `users`, `UserController::destroy()` checks `$user->transactions()->first()` and returns a `409` naming the transaction, the same pattern as Category/Product's guards — the other natural guard (blocking a user from deleting the account they're currently logged in as) is still open, since nothing enforces it yet even now that "the current user" exists. No `role`/permission field either, for the same reason: nothing checks one yet.
- **Authentication**: session-based, via Laravel's default `web` guard (`config/auth.php` — `'driver' => 'session'`, `Auth::attempt()`/`Auth::guard('web')->logout()`) rather than Sanctum API tokens — this is a server-rendered Blade app with same-origin `fetch()` calls, not a true SPA or mobile client, so a plain session cookie is the right primitive; Sanctum stays installed and otherwise unused, reserved for a future real API consumer. `LoginController` (non-resource, like `DashboardController`) has `create()`/`store()`/`destroy()`; `LoginRequest` validates `email`/`password` shape only — the actual `Auth::attempt()` call and its `ValidationException::withMessages(['email' => ...])` on failure live in the controller, keeping the FormRequest a plain validator like every other one in the app. There's no self-registration route — accounts are created through the User module (workshop 06), matching a POS where staff don't sign themselves up. **Route protection**: every route in `routes/web.php` except `/login` (wrapped in `Route::middleware('guest')`, so an already-authenticated visitor is bounced to `/dashboard` instead) sits inside `Route::middleware('auth')->group(...)`; `routes/api.php` wraps every `apiResource`/dashboard route the same way (leaving only the framework's default `/api/user` on its original `auth:sanctum` example). The root `/` route checks `Auth::check()` directly and redirects to `login` or `dashboard` — deliberately not a redirect-then-redirect through `/dashboard`. `bootstrap/app.php` sets `$middleware->redirectGuestsTo(fn () => route('login'))` (Laravel's default `Authenticate` middleware otherwise returns a bare `401` with no redirect target configured) and `$middleware->statefulApi()`. **`statefulApi()` is the one non-obvious piece**: `routes/api.php` runs under the `api` middleware group by default, which does *not* start a session — without this, `auth` middleware on an api.php route would never see the session `Auth::attempt()` created, so `/categories`'s own `fetch('/api/categories')` call would be treated as a guest request despite the browser already holding a valid session cookie. `statefulApi()` (backed by Sanctum's `EnsureFrontendRequestsAreStateful` middleware, already installed) turns on session/cookie/CSRF handling for `api.php` requests whose `Referer`/`Origin` header matches `config('sanctum.stateful')` (defaults to `localhost`/`127.0.0.1` plus `APP_URL`'s host — i.e. exactly the app's own frontend, nothing else) — this is the standard first-party-frontend recipe Sanctum ships for exactly this "Blade + fetch, not a real SPA" shape. Because that pulls in the same `VerifyCsrfToken` middleware the `web` group uses, every mutating (`POST`/`PUT`/`DELETE`) `fetch()` call across the frontend needs an `X-CSRF-TOKEN` header — each page's `<head>` carries `<meta name="csrf-token" content="{{ csrf_token() }}">`, and `resources/js/csrf.js` (a small helper module, *not* a `vite.config.js` entry point — importing a non-entry helper from multiple entry files doesn't break the "no shared entry" rule below, since Vite still bundles per-entry) exports `csrfToken()` for any module's fetch calls to read that meta tag.
